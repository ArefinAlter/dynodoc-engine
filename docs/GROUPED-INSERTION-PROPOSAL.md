# Optional grouping of concurrent workspace insertions

Status: a library experiment proposed in PR #39, revised after the 18 October
review. This does not replace the default insertion policy. No API handler, CLI
command or editor enables it.

The review records an existing design rule: same-position insertions sort by node
id and are marked for review. The default merge's existing position/id behavior
remains unchanged here; this proposal does not add those review markers.
See [the review](https://github.com/ArefinAlter/dynodoc-engine/pull/39) and the
[integration record](PROJECT-STATUS.md).

## Why offer a separate preference?

Two working copies can generate the same fractional positions. Their newly added
blocks may alternate after merging. Keeping each side's run together is a possible
reading preference, but putting the team run first is a policy choice, not a fact
about authorship, intent or ancestry. It therefore requires an explicit opt-in.

The library offers `merge_with_grouped_insertions` and
`merge_strict_with_grouped_insertions`. Ordinary `merge` and `merge_strict` retain
their existing behavior. Signed `dynodoc.same-file.node-field.v1` convergence uses
the entrypoint that preserves original insertion positions.

## Proposed rules

1. Finish whole-tree validation and, for strict merges, all existing-block choices.
   Group only when no conflicts remain. Grouping changes positions, never parents.
2. Scan siblings in `(position, node id)` order. A base sibling's original location
   still separates gaps if it was deleted or moved. This prevents edits in two
   original gaps from being treated as one insertion run.
3. Group only if the side changes at least twice in one gap, such as team/draft/team
   or draft/team/draft/team. Already ordered draft/team and team/draft runs stay put.
4. Keep the team's existing positions and both sides' internal order. Prefix each
   draft position with the team's last position in that gap.
5. Before allocating the concatenated keys, ensure each resulting position is at
   most 200 bytes. Also require every resulting key to precede the next separator.
   If either condition fails, preserve all existing positions in that gap.

The size bound applies only to keys generated by this experiment. Older or imported
long positions remain readable and are not truncated. Fallback can leave runs
interleaved. Repeated pulls with already ordered runs do not rewrite their keys.

## Compatibility and review gates

There is no migration, event codec or HTTP schema change. Previously recorded
events and stored positions are untouched. Default workspace merges and signed v1
insertion results are unchanged by this PR. A regression checks the ungrouped v1
result in both parent orientations while the explicit workspace variant groups it.

Before any consumer enables this preference, review the policy against the desired
same-position tie-break, test native `between()` with the resulting neighbors, and
define how a user selects and sees the preference. A 200-byte cap alone does not
establish native-editor acceptance. Adopting grouping in portable signed resolutions
requires a new strategy id and retaining the old verifier.

The earlier strategy-version decision covering other changes already merged into
the engine remains separate. This proposal does not certify offline convergence,
general operation independence or a whole-request memory bound.
